## Agent 1 — macOS capture APIs and timing evidence (2026-10-26)

Evidence level: primary documentation and source-code review only. No interactive input capture, permission prompt, overnight run, or timing calibration was performed by this research agent. “Observed” below means present in the linked documentation/source, not empirically verified on this Mac. Links to moving GitHub branches are research pointers, not pinned dependency versions. Proposed implementation is independently written; no third-party code was copied.

### Passive native collection

- **Observed:** Apple's [CGEventTapOptions](https://developer.apple.com/documentation/coregraphics/cgeventtapoptions) defines a passive listener as able to receive events without modifying or diverting them. [CGEventTapLocation](https://developer.apple.com/documentation/coregraphics/cgeventtaplocation) distinguishes login-session events from the earlier HID location. **Recommendation:** use `.cgSessionEventTap` with `.listenOnly`; never inject or suppress user input. A session stream may include remote or synthetic input, so call records “observed session input,” not proven hardware events.
- **Observed:** [tapCreate](https://developer.apple.com/documentation/coregraphics/cgevent/tapcreate(tap:place:options:eventsOfInterest:callback:userInfo:)) returns an optional port; denied event types can be removed from the requested mask, and creation may fail. It attaches to a run loop through a Mach-port run-loop source. Its permission discussion still references OS X 10.4. **Recommendation:** avoid treating those historical permission sentences as modern setup instructions; handle creation failure visibly.
- **Observed:** Apple exposes [CGPreflightListenEventAccess](https://developer.apple.com/documentation/coregraphics/cgpreflightlisteneventaccess()) and [CGRequestListenEventAccess](https://developer.apple.com/documentation/coregraphics/cgrequestlisteneventaccess()). An [Apple DTS answer](https://developer.apple.com/forums/thread/811443) identifies these APIs and CGEventTap as the supported modern Input Monitoring route, distinguishing it from Accessibility. Apple's [Input Monitoring help](https://support.apple.com/guide/mac-help/control-access-to-input-monitoring-on-mac-mchl4cedafb6/mac) places the user switch in System Settings → Privacy & Security → Input Monitoring. **Recommendation:** request only after a deliberate Start action; display denied/needs restart states; do not request Accessibility unless optional AX context actually needs it. The owner must grant OS permission manually.

### What “exact timing” can mean

- **Observed:** [CGEventTimestamp](https://developer.apple.com/documentation/coregraphics/cgeventtimestamp) is an unsigned nanosecond count since startup. **Derived design:** preserve that original integer in each record, plus sequence, capture-session ID, wall-clock anchor, and callback receipt time if available. Subtract event timestamps for intervals; do not subtract formatted wall-clock strings. Nanosecond representation does not establish nanosecond physical accuracy: keyboard scan/debounce, transport, OS scheduling, and event coalescing remain unmeasured.
- **Observed:** [keyboardEventKeycode](https://developer.apple.com/documentation/coregraphics/cgeventfield/keyboardeventkeycode) identifies the virtual key, while [keyboardEventAutorepeat](https://developer.apple.com/documentation/coregraphics/cgeventfield/keyboardeventautorepeat) distinguishes repeat key-downs. **Derived timing definitions:** dwell = matching key-up minus first nonrepeat key-down; down-to-down interval = next nonrepeat down minus preceding nonrepeat down; flight = next down minus preceding key-up. Flight may be negative during overlap. Never reset a held key's start on autorepeat. Preserve repeats as separate records. Retain incomplete pairs with a reason instead of inventing releases.
- **Recommendation:** keep raw down/up records alongside derived holds. At pause, permission loss, secure-input gaps, sleep, tap disable, queue loss, or restart, close the segment and invalidate pending key/button pairs. This avoids reporting an hours-long hold after wake. Use modifier-change records and raw flags; modifier edges inferred from `flagsChanged` need independent testing, especially simultaneous left/right modifier keys and Caps Lock. Standard key-up events do not cover every special/media key.
- **Inference:** virtual keycode plus event Unicode is not an authoritative document transcript. Input methods, dead keys, dictation, paste, autocorrection, shortcut handling, application edits, and synthetic events can change committed text. Label Unicode as event text and app context as a sampled association. Do not promise every final character or infer clipboard contents from a paste shortcut.

### Mouse, movement, and scroll

- **Observed:** [CGEventType](https://developer.apple.com/documentation/coregraphics/cgeventtype) includes left/right/other button down/up, move/drag, scroll, and tap-disabled notifications. [CGEventField](https://developer.apple.com/documentation/coregraphics/cgeventfield) describes button numbers, matching mouse event numbers, click count, movement deltas, pressure, and several scroll representations. Pressure may be tablet-generated; it is not universal finger force.
- **Derived design:** calculate button hold from a matched down/up, retaining button and event number. Capture cursor coordinates, raw deltas, click count and drag events; record screen geometry changes so multi-monitor coordinates remain interpretable. Preserve line, pixel, and fixed-point scroll fields with their units, plus continuous/phase/momentum information when supplied. A scroll event does not prove a physical mouse wheel; trackpads and momentum can generate it too.
- **Recommendation:** movement can dominate a half-week dataset. Use a bounded ingestion queue; if overwhelmed, count and emit a gap record and invalidate active pairs. If movement is deliberately sampled/coalesced, record the policy in session metadata and retain clicks/keys at full event granularity. Never call sampled traces complete raw motion.

### Secure input, context, and long sessions

- **Observed:** Apple's archived [TN2150](https://developer.apple.com/library/archive/technotes/tn2150/_index.html) explains that Secure Event Input prevents keyboard interception, including event taps. It is historical documentation but establishes the platform's protection model. **Recommendation:** respect it; record a gap/status transition and reset state. `IsSecureEventInputEnabled` is used by Hammerspoon to detect this condition. Do not attempt to bypass secure fields or fill missing sensitive content.
- **Observed:** [NSWorkspace activation notifications](https://developer.apple.com/documentation/appkit/nsworkspace/didactivateapplicationnotification) provide an `NSRunningApplication`; they must be observed through the workspace notification center. [NSWorkspace](https://developer.apple.com/documentation/appkit/nsworkspace) provides sleep/wake and session-active transitions. **Derived design:** cache app identity outside the event callback; emit context-change records with their own timestamp; use these transitions to delimit recording and reconstruct/recheck taps on wake. App identity alone does not expose the website, focused control, caret, or meaningful document context. A context snapshot near an event may race an app switch; do not represent it as atomically guaranteed.
- **Recommendation:** keep the tap callback short: extract primitive fields and enqueue; perform JSON encoding, file writes, optional AX queries, and menu updates elsewhere. A bounded queue and asynchronous writer are appropriate, provided overflow and write failure are visible. Start the writer before creating the tap. On Off, stop ingestion first, then drain/flush and invalidate holds. An asynchronous drain must preserve ordering across rapid Off/On toggles. Rotate JSONL files and flush periodically; a crash can lose buffered records, so the format must tolerate a final truncated line. On disk failure show an error and stop capture instead of continuing under a recording indicator.

The proposed Swift menu-bar app, passive session tap, NSWorkspace context cache, bounded asynchronous local JSONL writer, and explicit On/Off control are a reasonable first collection layer. This verdict is an engineering inference from the sources, not evidence that this implementation is working. ## Agent 3 — event persistence and ActivityWatch comparison

**Primary sources inspected (2026-10-26):**
- [ActivityWatch/aw-watcher-input](https://github.com/ActivityWatch/aw-watcher-input): desktop input watcher, explicitly aggregates counts instead of recording key identity. It is an architectural comparison, not a replacement for raw training capture.
- [Watcher implementation](https://github.com/ActivityWatch/aw-watcher-input/blob/master/src/aw_watcher_input/main.py): separate keyboard/mouse listeners feed UTC-timestamped ActivityWatch events. Its five-second aggregation and source comments about counting both transitions show why that schema cannot reconstruct individual hold durations. Read the source rather than assuming “input tracking” means full-fidelity capture.

**Implementation decisions in this repository (our choices, not claims from ActivityWatch):**
- Preserve ordered raw down/up events plus a monotonic nanosecond timestamp; keep UTC wall time separately. Wall-clock jumps must not change measured typing intervals. Derive down→up holds and down→next-down intervals in analysis, with autorepeat excluded from new presses.
- Store newline-delimited JSON so each completed line can be streamed and inspected. A bounded producer queue moves encoding, append, synchronization, and rotation off the event callback. Rotate on UTC event date or 64 MiB by default. Abrupt power loss can lose the unsynchronized tail; periodic synchronization reduces that window and does not promise crash-proof writes.
- Default recordings live under `~/Library/Application Support/Ghost Recorder/Recordings`, outside the public checkout. App/recording directories are 0700 and recordings are created 0600. The source repository can be public while personal input stays local.
- Queue overload is observable through counters and explicit `data_loss` stream markers. Stop rejects new enqueues immediately, drains accepted events, synchronizes/closes files, then completes. Disk failures become a failed state and an error string for the menu UI.
- A training pipeline must invalidate partially held keys/buttons at stop, sleep/lock, privacy exclusions, permission loss, or data-loss boundaries. Never pair a release with a press across such gaps. Secure input may be unavailable; missing data cannot honestly be represented as complete capture.
- Minimal context fields are foreground app identity/name and window title when available. These are context hints, not guaranteed target element labels, browser URLs, screenshots, or the application's final committed text. Input events do not establish what was actually entered after IME composition, shortcuts, edits, or application transformations.

**Scope:** this collector creates the dataset foundation. A click-prediction model still needs explicit target labels, time-separated evaluation, and comparison with simple baselines; recording alone does not produce a validated model.


## Specialist 2 — Timing features and the prediction research path

Research date: 2026-10-26. Primary repositories, author papers, and official documentation were read. These are design references; no external implementation or dataset was copied into this repository.

### Timing measures that answer the collection request

[Killourhy and Maxion, CMU Keystroke Dynamics Benchmark](https://www.cs.cmu.edu/~keystroke/) defines hold time H as key-up minus its matching key-down, DD as consecutive key-down intervals, and UD as the next key-down minus the preceding key-up. UD is signed and can be negative when keys overlap; H + UD = DD for the same pair. The benchmark includes 51 people over eight sessions with at least a day between sessions. Its external timer was validated separately, illustrating why timestamp resolution alone does not establish collection accuracy. It is fixed-password authentication research, not evidence of arbitrary next-word prediction.

Implementation implication: retain physical down/up events and monotonic timestamps, ignore repeat key-downs for physical dwell, and preserve simultaneous keys rather than treating typing as a sequence of non-overlapping holds. Do not join key-downs and releases across paused, secure, locked, dropped, or restarted capture segments. Report missing matches instead of manufacturing durations. This is our design inference from the definitions and operating conditions.

### GitHub projects worth inspecting

- [spaansba/ForesightJS](https://github.com/spaansba/ForesightJS) predicts browser interaction intent for prefetching using pointer trajectories, tab navigation, and scrolling. Its [official explanation](https://foresightjs.com/docs/vue/behind-the-scenes/) describes a bounded position history and linear extrapolation, and the [official introduction](https://foresightjs.com/docs/getting_started/intro) shows registration of known DOM targets. Useful: start with an explicit geometric baseline and known target bounds. Limitation: browser-visible elements and prefetch callbacks differ from system-wide personal action prediction; it supplies no evidence that half a week of global input yields a complete desktop model. [License](https://github.com/spaansba/ForesightJS/blob/main/LICENSE): MIT, copyright Bart Spaans; copying substantial code requires retaining notices. No code copied here.
- [abhijitmajumdar/Mouse_tracking_predictor](https://github.com/abhijitmajumdar/Mouse_tracking_predictor) is a concrete LSTM trajectory demo. It uses 16 preceding normalized positions to predict a seventeenth and can roll predictions forward. Its author explicitly describes the result as a demonstration that does not accurately predict user motion. Useful: supervised windows and clear distinction between one-step and rolled-out prediction. Limitation: drawing-area trajectory coordinates do not identify the next clicked UI control. A license was not visible in the inspected root, so treat it as a conceptual reference rather than reusable code until permission is verified.
- [ericyoc/behavioral_keystroke_dynamics_baseling_poc](https://github.com/ericyoc/behavioral_keystroke_dynamics_baseling_poc) presents phrase-based behavioral authentication and comparisons with Manhattan, Mahalanobis, and SVM approaches on the CMU data. Useful: simple timing baselines before complex models. Limitation: identifying whether a phrase matches a person's rhythm does not forecast their next key or click. Verify its current license and dataset permissions before reusing files; this implementation does not import either.

### Directly relevant action-prediction papers

[Matti, Dillenbourg and Novelli, A Click Ahead (2023)](https://arxiv.org/html/2309.12170v1) is unusually close to the proposed product. It records one Windows dual-monitor user's week (46.21 hours, 86,284 actions), creates semantic action identities using keyboard/modifier combinations and visual patches of clicked controls, and conditions an RNN on the previous five actions plus app and cursor/window context. Rare controls are filtered; the resulting action vocabulary has 442 classes. The reported best validation accuracy is 34.63%. Its method also exposes layout/appearance matching failures. This is a narrow feasibility result for one user and representation, not a guarantee for this user or a half-week capture. We should infer that semantic target labels and context matter, not that coordinate logs alone reproduce the result. We deliberately do not implement its screenshot patches or cursor attraction in this collection tool.

[Ziebart, Dey and Bagnell, Probabilistic Pointing Target Prediction via Inverse Optimal Control (IUI 2012)](https://www.cs.cmu.edu/~bziebart/publications/pointing-target-prediction.pdf) treats partial pointing trajectories as evidence for intended targets, with personalized/context-dependent trajectory dynamics and probabilistic target beliefs. The work highlights closely spaced targets, latency, uncertainty and variation across users/devices. Practical inference: direction extrapolation alone is a useful baseline, while later target inference should include candidate geometry, velocity/acceleration and uncertainty. The paper is a research reference, not a redistribution license for implementation assets.

### What the repository implements now

`scripts/analyze.py` is original, standard-library-only offline code. It streams JSONL timing events, summarizes dwell/DD/signed UD and mouse holds, produces a coarse click heatmap, and trains a deliberately modest personal count model: current app + previous click cell -> next click cell. Screen coordinates are absolute points, including negative coordinates on additional displays; cell size is fixed before training. It abstains below configurable support and never emits text, window titles or screenshots in summaries. Summaries/models remain private outside this public repo with restrictive creation permissions.

Its evaluation uses an oldest-prefix training set and later holdout without training on test labels, reporting top-1/top-3 accuracy, abstention/coverage, and an app-popularity baseline. [scikit-learn's official TimeSeriesSplit guidance](https://scikit-learn.org/stable/modules/generated/sklearn.model_selection.TimeSeriesSplit.html) explains the core issue with ordinary random cross-validation on ordered data: it can train on the future and test on the past. The included analyzer does not depend on scikit-learn. Our split is by observed click order, not an equal-duration statistical fold; daily blocked evaluation would be the next step once multiple days exist.

### A staged path to a stronger Ghost Typer feature

1. Validate collection quality using a small known key/mouse sequence, overlap tests, pause/resume and sleep tests. Establish event-loss and permission behavior before collecting days of data.
2. Gather several real work sessions with explicit session/context boundaries; reserve the latest unseen day or days. Keep capture distributions and rare/new-target rates visible. A half-week is an initial sample, not a completion criterion.
3. Benchmark the shipped app/cell-count model, app popularity, last-target repetition, and short-history Markov models. Fix settings on training/validation days, then evaluate untouched future days. Report coverage together with accuracy so abstention cannot hide failures.
4. Add explicit app/window-relative geometry and stable semantic target IDs through permitted UI accessibility APIs where available. Separate text entry, navigation shortcuts, clicks, drags, scrolling, and switching apps. Physical key rhythms and intended action identities need different features.
5. Only after simpler baselines justify it, compare a small GRU/LSTM with the same temporal holdout. Use recent action sequence, elapsed time, app, candidate-target geometry, and optional pre-click trajectory features. Fit coordinate normalization only on training information and respect display-layout changes.
6. Measure calibration, top-k hit rate, new-target handling, latency and benefit in a suggestion-only interface. Keep abstention and owner control; a forecast should not automatically execute a click. No reported paper metric establishes this project's accuracy before it is measured on its own held-out recordings.


## Agent 1 — resumed verification: lifecycle limits and acceptance checks

Rechecked 2026-10-26 against Apple documentation (including its published Markdown representation) and current Hammerspoon source. This is documentation/source review, not an empirical long-running capture test.

- **Session switching is distinct from locking.** Apple documents [sessionDidResignActiveNotification](https://developer.apple.com/documentation/appkit/nsworkspace/sessiondidresignactivenotification) as a user session switching out. This alone does not establish a lock-screen guarantee. [Hammerspoon’s watcher source](https://github.com/Hammerspoon/hammerspoon/blob/master/extensions/caffeinate/libcaffeinate_watcher.m) separately registers session-active changes and distributed lock/unlock names (`com.apple.screenIsLocked` / `com.apple.screenIsUnlocked`). Those lock names are practical source evidence, not a documented Apple API contract. Verify behavior on the target macOS; do not silently equate session switching with every lock transition.
- **Sleep is a segment boundary.** Apple’s [willSleepNotification](https://developer.apple.com/documentation/appkit/nsworkspace/willsleepnotification) and [didWakeNotification](https://developer.apple.com/documentation/appkit/nsworkspace/didwakenotification) must be registered on `NSWorkspace.shared.notificationCenter`. On sleep, reject input, invalidate pressed-state pairs, and flush; on wake, refresh context and tap health before accepting events. This ordering is our design recommendation, not an Apple guarantee of event completeness.
- **Permission status is not capture-quality proof.** [CGPreflightListenEventAccess](https://developer.apple.com/documentation/coregraphics/cgpreflightlisteneventaccess()) exists from macOS 10.15 and returns a Boolean. Even an allowed status does not establish that every requested event type is flowing. Keep a visible failure state for tap-creation failure and writer errors; test actual down/up delivery using an owner-initiated known sequence.
- **Secure input is a platform boundary.** [TN2150](https://developer.apple.com/library/archive/technotes/tn2150/_index.html) describes event-tap keyboard suppression during secure input. Periodically checking secure-input state can annotate gaps but can miss transitions between polls. It cannot prove that all recorded ordinary text is nonsensitive, or identify every app’s protected custom control. Pause entire recording during detected secure input; never bypass the protection or manufacture missing text.
- **Passive really means passive.** Apple’s [CGEventTapOptions](https://developer.apple.com/documentation/coregraphics/cgeventtapoptions) establishes the passive option’s inability to alter or divert input. A recorder should remain `.listenOnly` and contain no event-injection implementation.

### Manual checks still needed on the owner’s Mac

The collector should ship with these checks marked unverified until performed, rather than presenting build success as capture validation:

1. Start/Off should visibly change status; no input records should be accepted after Off. Rapid Off/On must separate recording sessions and drain earlier records in order.
2. Press/release one key and one mouse button for a known short hold; verify ordered raw down/up plus plausible dwell. Test overlapping keys, autorepeat, two held modifiers, Caps Lock, drag, and negative flight intervals separately.
3. Lock/unlock, sleep/wake and fast user switching must create a gap and prevent a pre-gap down from pairing with a post-gap release. Wake while still locked must not resume capture prematurely.
4. With the owner’s chosen secure field, verify protected input is absent and that a gap/status is visible where detectable. Do not type a real password for the test.
5. Revoke Input Monitoring, make storage unavailable in a controlled test directory, and force queue overflow in synthetic tests. The status must stop claiming healthy recording and gaps must remain machine-readable.
6. Leave a short normal recording running before collecting half a week; inspect rotation, disk growth, CPU usage and event-loss counters. A multi-day reliability claim requires a real multi-day run.


## Storage specialist follow-up — raw events, local boundaries, and metadata

Primary sources inspected again on 2026-10-26; recommendations below are our engineering choices rather than guarantees from these projects.

- [ActivityWatch's data model](https://docs.activitywatch.net/en/latest/buckets-and-events.html) groups events by producer/schema metadata, represents event time in UTC, and merges adjacent identical context through heartbeats. [ActivityWatch/aw-core](https://github.com/ActivityWatch/aw-core) separates event types, datastore, transforms, and queries. **Application:** keep a versioned raw event schema and context transitions, then derive features offline. Heartbeat merging is suitable for unchanged app context, but applying it to physical key/button edges would erase the boundaries needed for hold and inter-key timing. Do not treat ActivityWatch's aggregated events as a drop-in exact-keystroke dataset. aw-core identifies MPL-2.0 licensing; this recorder adds no dependency or copied implementation.
- [OpenAdaptAI/openadapt-desktop](https://github.com/OpenAdaptAI/openadapt-desktop) documents a local engine, explicit recording upload, storage inspection/cleanup commands, and visible tray state for its optional shadow mode. Its shadow buffer has a separate lifecycle and encryption; those are properties of that project, not claims about Ghost Recorder. The project identifies MIT licensing. **Application:** give collection visible On/Off state, expose where files live, and keep raw collection separate from training and public source. A half-week recorder needs deliberate persistence; copying a short-lived shadow buffer policy would fail the owner's intended retention period.
- [OpenAdapt's privacy notice](https://openadapt.ai/privacy-policy) explicitly distinguishes local engine artifacts from optional hosted recording, warns that input/screenshot artifacts can include private values, and says compilation does not de-identify recordings. **Application:** public code and local recordings must have separate destinations. Local-only collection does not mean encrypted storage, and exporting or compiling raw data does not sanitize it. Ghost Recorder's JSONL permissions restrict ordinary access by other accounts; they do not protect against the same user, administrator, backup tools, or disk compromise.

**Implemented storage refinements:** event records retain optional pressure, click count, movement deltas, source PID, and keyboard type with explicit snake_case JSON field names. Unknown measurements are omitted. These fields describe the OS event when supplied; pressure is not a universal measurement of physical finger force, and source PID does not establish the foreground application. UTC formatting uses one locked formatter instead of constructing one per input event. A data-loss marker removes per-input payload fields and makes the lost count explicit. Existing monotonic timestamps remain the basis for intervals.

**Acceptance criteria for multi-day collection:** bounded queue overflow must produce a loss boundary after preceding accepted records; Stop must reject new input and flush accepted records before completion; disk failure must become a visible failed state; a still-running recorder must flush automatically; file rotation must preserve records with 0600 files inside a 0700 recording directory. Concurrent producers may interleave, but each producer's accepted order must remain intact. Automated tests cover these storage properties; hardware permissions, OS event completeness, secure-input behavior, and real elapsed-time accuracy require separate manual verification.


## Specialist 2 follow-up — independent project checks and analyzer validation (2026-10-26)

Evidence level: primary project documentation plus synthetic local tests. No half-week recording or real-user prediction experiment has been performed. The following projects were inspected as design comparisons; no external code or datasets were copied.

- [andyed/clicksense](https://github.com/andyed/clicksense) records button-down/up duration and summarizes pointer approach velocity, deceleration, corrections, distance and pause from a bounded recent history. Its browser implementation also extracts DOM targets and distinguishes drags. **Useful design:** keep pointer history bounded and retain both button transitions. **Caution:** the README's interpretation of these measurements as confidence is a project claim, not established ground truth for this user's intent. A click's final hold duration is available only after release; including it to predict that same click would leak the answer's future. For pre-click prediction, restrict features to events observed before the decision cutoff.
- [mikolofton/mouse-movement-prediction](https://github.com/mikolofton/mouse-movement-prediction) fits a per-user linear relationship between movement time and a Fitts-style difficulty index using distance and target width. **Useful design:** compare a small personalized model before deploying a large sequence model. **Limit:** this predicts movement duration for an already specified target, not which control the person will click next. Its custom confidence score is described as arbitrarily weighted pending testing; do not reuse it as calibrated probability.
- [spaansba/ForesightJS](https://github.com/spaansba/ForesightJS) demonstrates geometric intent prediction for registered browser elements. **Inference for a later Ghost Typer model:** candidate target bounds and identities are crucial if the goal is semantic next-control prediction. An absolute screen-cell baseline cannot infer the meaning of a control or reliably follow moved windows. Neither this project nor the other two establishes that this user's half-week sample will produce an accurate general desktop predictor.

**Original analyzer validation performed:** `python3 -m unittest discover -s tests_python -v` passed 20 synthetic tests. They exercise overlapping keys, signed flight, repeats, key/mouse pairing, invalid-event and explicit gap resets, session clock restart, chronological rejection, app changes observed on non-click events, start contexts, sparse-context abstention, exclusion of future target labels from training, private 0600 report/model creation, overwrite refusal, no raw text/title/name copying, UUID-independent file order, and rejection of malformed/truncated/non-object JSON before creating a report.

**Specific follow-up fix:** A click in app A, a context/key event in app B, then a click back in A must not become a direct A-to-A previous-click transition. The analyzer now resets previous-click history when any event reveals a changed app, and when an explicit context event has unknown app identity. Physical holds still use down/up pairing across ordinary app changes; explicit recording/data-loss boundaries invalidate them.

**How to use the first half-week honestly:** First inspect coverage, dropped-event counts and unmatched edges. Treat the data as an initial personal timing sample. Keep at least one later day untouched for final evaluation, report per-app support and abstention, and compare next-click predictions with the app-popularity baseline. The built-in fixed chronological holdout is exploratory; tuning grid size or support repeatedly against that holdout makes it development data. No accuracy figure can be claimed until actual held-out observations exist.


### Specialist 2 integration correction — two timestamp sources

Code review found that input records retain CGEvent occurrence timestamps while context/display/boundary metadata uses receipt uptime. A newer context record can precede an older queued input in stream order. The analyzer therefore validates chronology only between input records (key/flags/mouse/scroll), ignores metadata for that baseline, and resets the baseline plus pending holds on recording/data-loss boundaries. It never sorts away context order. Three added synthetic integration regressions cover preserved key holds through newer metadata, retained app-switch resets, genuine input-input reversal rejection, and pending-hold invalidation at a boundary. The full Python suite now passes 23 tests. This is synthetic integration evidence, not a long-duration capture result.

## Coordinator — implementation decisions and Ghost Typer fit

- Local checkout inspected: Ghost Typer's `typing_profiler.py` records press timestamps and modifier state, then uses releases only to update held modifiers. It cannot recover a physical key's down-to-up duration from its existing `KeyEvent` model. This recorder therefore keeps raw down/up events separately and adds mouse input instead of extending that short-session profiler in place. Observation is from the existing local source; no original Ghost Typer source was changed.
- [KeyCastr](https://github.com/keycastr/keycastr) documents opt-in macOS Input Monitoring, keyboard and optional mouse event visualization, and permission/restart troubleshooting. It provides evidence that a visible, permissioned native input utility fits this platform. Its README identifies BSD-3-Clause licensing; its code was not copied. It is a visualizer rather than a personal next-action predictor.
- [Apple SMAppService.mainApp](https://developer.apple.com/documentation/servicemanagement/smappservice/mainapp) is the official main-app login-item mechanism. Implementation choice: login launch and recording resume are separate explicit menu toggles. Initial app launch remains OFF; recording starts only after the user's notice/permission flow. No LaunchAgent is installed behind the menu.
- Implementation uses Swift + Apple frameworks, without external runtime dependencies: a passive listen-only session event tap, visible menu bar state, optional Unicode event text/window titles, sampled app metadata, bounded async JSONL writer and offline Python analysis. No new global clipboard handler or interaction with Ghost Typer's Forge checkout/automation was added.
- Capture does not query focused-field values or scrape documents. Context is app identity plus optionally accessible focused-window title, sampled on activation and at 500 ms. This is deliberately labeled approximate, not full semantic context. A richer semantic model would need separately authorized, timestamped UI labels (and evaluation of context races) before it can claim to predict actual controls.
- Lifecycle gaps discard queued input older than the new capture epoch. Secure-input, observed lock/sleep, disabled taps and writer overflow mark continuity loss. There is no attempt to bypass OS restrictions. The public code repository excludes recordings and derived JSON; recordings live in a separate user Library directory.
- Source PID is event-source metadata, not a reliable target-application label. Modifier flags changes remain raw; current analysis derives dwell only for normal key-down/up pairs. Pressure and event metadata can be absent/zero depending on device and OS support.

### Verification scope

Synthetic storage and offline analysis checks validate event encoding, owner-only file permissions, ordered asynchronous writes, bounded queue loss, file rotation, shutdown drain, disk-error reporting, repeats, overlapping keys, mouse holds, app-change resets, sparse-data abstention and chronological model evaluation. They do not establish real-world prediction accuracy or certify multi-day capture completeness. Input Monitoring, Accessibility availability, secure fields, lock/wake, IMEs and device event rates require target-Mac checks. No personal dataset has been collected as part of implementation.

### Coordinator final packaging and review evidence

Eight Swift storage tests and 23 Python timing/model tests passed on synthetic data after final source review. Common-mode context/health timers and explicit menu enablement were corrected. Initial strict signing failed on FinderInfo metadata attached by the Documents File Provider; a later attempt showed that it could be reattached between cleanup and verification. Packaging now signs in a temporary folder outside that provider, verifies the staged bundle, archives without extended attributes, extracts the ZIP and verifies that extracted bundle again. This validates the packaged code signature, not live input behavior or notarization. See `docs/VERIFICATION.md` for exact owner checks. Live menu/recording verification was deliberately skipped, permissions were not granted, and no personal training capture was started.
